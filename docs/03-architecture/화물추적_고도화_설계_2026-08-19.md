# 화물추적·스케줄변경알림 고도화 설계

작성 2026-08-19 · 근거: KLNET LogisView 2.0 매뉴얼 2부 전문 분석(글로벌화물추적·스케줄변경알림)
+ 경쟁사 조사(씨벤티지·트레드링스·project44 계열) + 자사 데이터 자산 실측

## 0. 한 줄 요약

KLNET 스케줄변경알림의 원료는 **터미널 선석스케줄**인데, 그것은 우리가 이미 16개 터미널에서
하루 2회 수집하고 있다. 여기에 KLNET에 **없는** 선사 이벤트 API 6사를 얹어
**이중 소스 교차검증(선사 ETA × 터미널 ETB)** 이라는, 국내 어느 서비스에도 없는 축을 세운다.

## 1. KLNET 분석 요약 (매뉴얼 실측)

### 글로벌화물추적 (6p)
- 5구간 추적: 국내내륙 → 국내터미널 → 해상 → 해외터미널 → 해외내륙
- MBL/HBL 교차등록 · BL 일괄등록(엑셀) · 월구독 구간선택 과금
- 그리드: STATUS(EMPTY 반출/POD 도착/RAIL 운송 중…) + ROUTE 도트 진행바(선박 아이콘)
  + POL(ETD,ATD)/POD(ETA,ATA) E/A 마커 + 선박위치·메일알림·상단고정·상세(+)
- 상세: 컨테이너별 GATE OUT(Empty)/GATE IN(Full)/INLAND 출발·도착/POD GATE OUT/IN
- 선사 38사 오픈 (MAEU 계열 중복 포함)

### 스케줄변경알림 (16p)
- 원료: **적하목록신고**(화주·선적정보) × **터미널 선석스케줄**(ETB/ETD) 매칭
- 수출: ETB/ETD/모선 변경 감지, ATD 수신 시 종료 · 수입: ETB 변경, ATB 수신 시 종료
- 알림조건: 날짜 변경(시/분 무관) · 이력조건: 날짜+시 변경
- 화면: 현재상태 그리드 + HISTORY 그리드(변경값 빨간색) + 이메일 다중수신(수출Y/N·수입Y/N)
  + PDF 공문(Vessel Schedule Change History) + AIS 지도
- 한계(공식 명기): "KL-Net으로 적하목록 신고한 선적건만 조회 가능" — **자사 EDI 고객 전용**

## 2. 자산 대차대조표 — 왜 이길 수 있나

| 원료 | KLNET | 태웅 Control Tower |
|---|---|---|
| 터미널 선석스케줄 | 자사 EDI 연계 터미널 | `bs_vessel_calls` **16터미널 × 35일 일자별 이력** (부산신항7·북항2·인천2·광양2·평택당진2·대산1) |

| 변경 이력 | 터미널 ETB/ETD | `bl_change_log`(필드별 old→new) + `bl_snapshot`(폴링별 전체 스냅샷) — **선사발 변경** |

| 반입마감(CCT) | ✗ | `bs_vessel_calls.cct` — **KLNET에 없는 필드** |

## 3. 서비스 설계 — 3대 축

### 축 A. Voyage Canvas — 항로 SVG 시각화 (감탄 포인트)

KLNET 은 도트 진행바 + 클립아트 배. 우리는 **손으로 그린 SVG 한 장**으로:

- 항구 노드(UNLOCODE + 항구명 + 일시), 구간 아크(bezier 항로 곡선)
- **실적(ACT) 구간 실선·채움 / 예정(EST) 구간 점선** — 이벤트 기반 진행률로 선박 마커 배치
- 환적항은 중간 노드로, 선박 마커에 선명·항차 라벨
- 현재 항해 구간에 dash-flow 애니메이션 (prefers-reduced-motion 존중)
- 다크/라이트 테마 토큰 사용, 뷰박스 기반 반응형 (모바일 = 세로 스택 폴백)

### 축 B. 스케줄변경알림 2.0 — 이중 소스 교차검증

**B-1. 선사발 변경 (기존 자산 노출)** — bl_change_log/bl_snapshot 은 이미 쌓인다.
화면이 없었을 뿐. KLNET HISTORY 그리드 대응 + 초과:

- BL 상세 패널: 변경 타임라인 (ETD/ETA/모선 old→new, 빨강/초록 diff)
- **ETA 드리프트 차트(SVG)**: 폴링 시점 x축, ETA 값 y축 — "도착일이 어떻게 밀려왔나" 한눈에.
  KLNET 표에는 없는 시각화. 씨벤티지 유료 기능 급.
- 감시 그리드 위 **이슈 피드**: 내 화물 전체의 최근 변경 통합 (기준일시·이슈·BL·구간·old→new)

**B-2. 터미널발 변경 (신규 파생)** — bs_vessel_calls 일자별 이력을 비교하면
수집일 간 ETB/ETD/선석 변동이 나온다. 수출 화물의 국내 구간은 선사 API보다
터미널이 빠르고 정확하다(KLNET 설계 사상과 동일 — 단 우리는 16터미널).

**B-3. 교차검증 배지** — 같은 모선·항차에 대해 선사 ETA와 터미널 ETB가 12h 이상
어긋나면 "소스 불일치" 경고. 아무 데도 없는 기능. 포워더의 실무 감각(어느 쪽을 믿을지)을
데이터로 대신한다.

### 축 C. 국내 터미널 연계 — 단거리 보완 (사용자 지시 반영)

추적 결과의 선명+항차를 bs_vessel_calls 와 자동 매칭:

- 수출(POL=KR·신항/북항/인천/광양/평택/대산): 접안(ETB)·출항(ETD)·**반입마감(CCT) 카운트다운**
- CCT 는 화주가 가장 아쉬워하는 값 — KLNET·트레드링스 모두 없음
- 매칭 실패 시 조용히 생략 (오탐 배지 금지)

## 4. 데이터 흐름

```
[선사 API 6사] ──carrier-track──> 조회 화면 ─┐
     │ (08:20/20:20 폴링)                    ├─> Voyage Canvas + 게이트 9슬롯
     └─> bl_snapshot / bl_change_log ────────┼─> 변경 타임라인 + ETA 드리프트
[16터미널 선석] ──TWL_BerthUpload──> bs_vessel_calls (35일 이력)
     └─ 선명+항차 매칭 ──────────────────────┼─> 국내구간 패널(ETB/ETD/CCT) + 교차검증 배지
[AISStream] ──> vessel_positions ────────────┘   (vessel.html 딥링크)
```

프론트 접근: bs_vessel_calls 는 publishable key 직접 REST(berth.js 기존 패턴),
변경 이력은 bl-watch 함수 `action=detail`(권한 검사 内藏) — **서버 변경 최소화**.

## 5. 퍼블리싱 정의

### 화면 구조 (cargo.html)

> **구현 결과는 아래 계획보다 한 걸음 더 갔다(2026-08-19 UX 개편).** 조회 히어로와 상시 노출 바로가기
> 카드는 **좌측 고정 레일 + 서랍**으로 바뀌었고, 결과 카드는 **운송 관제 티켓** 한 장으로 통합됐다.
> 현재 화면 사양은 `docs/04-design/화면기획_화물추적.md` 가 정본이다. 아래는 착수 시점의 계획으로 남긴다.

1. 조회 히어로 (기존 유지)
2. **결과 카드** = ①헤더(BL·선사·상태배지·선명) ②Voyage Canvas(SVG) ③국내 터미널 패널(조건부)
   ④컨테이너 게이트 9슬롯 표 ⑤전체 이력(접기) ⑥데이터 시점 푸터
3. **감시 섹션** = 이슈 피드(최근 변경 통합) + 감시 그리드(기존) + BL 상세 확장(변경 타임라인 + ETA 드리프트)
4. 바로가기 카드 (기존 유지)

### 컴포넌트 규격
- SVG 는 전부 인라인 + `currentColor`/CSS 변수 — 테마 자동 대응, 외부 이미지 0
- 카드 내 표는 `overflow-x:auto` 래퍼 필수 (모바일 가로 스크롤 격리)
- 배지 체계: 상태(is-wait/is-move/is-done) 기존 + 신규 `is-warn`(교차 불일치)·`is-cct`(마감 임박)
- 타이포·간격: 기존 style.css 토큰 준수, 신규 클래스는 `vc-`(Voyage Canvas)·`sc-h`(schedule history) 프리픽스
- i18n: 신규 문자열 전부 data-i18n (ko/en/zh 3언어 동시 등록 — 2026-08-18 감사 기준 유지)
- 접근성: SVG `role="img"`+`<title>`, 애니메이션 reduced-motion 미디어쿼리 가드

### 반응형
- ≥900px: Canvas 가로형(항구 노드 수평 배열) · <900px: 세로 타임라인형으로 전환
- 감시 그리드·이슈 피드: 기존 그리드 반응형 규약 그대로

**되살릴 때 필요한 것은 코드가 아니라 근거다**: 산출 SQL 은 git 이력에서 되살릴 수 있고

그대로 유효하다. 다만 재도입 전에
"이 지표로 무엇을 결정하는가"를 먼저 정할 것 — 그 답이 없어서 지운 기능이다.

## 8. 조사 반영 백로그 (연구·실사 근거)

### P7 정시율 지표 — Sea-Intelligence GLP 호환 공식 (논문·업계 방법론 실사)
- 기준 ETA(B2) = **POL 출항 시점의 ETA** (GLP pro-forma 정신에 최근접) · 보조로 B1(등록시)·B3(도착직전)
- `on_time_pct` = |ATA−B2| ≤ ±1일 비율 (글로벌 참고치 2025-26: 59~66%)
- `avg_delay_late` = 지연 건만의 평균(조기도착 상계 금지 — GLP 규칙, 참고치 5.3~5.5일)
- `eta_drift` = B3−B1 (누적 슬립) · `revision_count` · 선사별 낙관/비관 편향
- **D-k 정확도 곡선**: D-14/7/3/1 시점 ETA 의 중위 오차 — "어느 선사 약속으로 육상운송을 잡아도 되나"
- 표본 10건 미만 셀 회색 처리 + Wilson 95% CI · 항차 단위 매크로 평균 · 체선 대기 건 분리 집계
- 원료: bl_snapshot(폴링별 ETA) + ATA 이벤트 + bs_vessel_calls(ATB) + ELVIS 295k

### 도입 후보 (씨벤티지 실사에서 확인된 가치 기능)
